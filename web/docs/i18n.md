# Internationalization & RTL

## Framework

The project uses [next-intl](https://next-intl.dev) v4 for internationalization, integrated with Next.js App Router.

## Configuration

### `src/i18n/routing.ts`

```typescript
export const routing = defineRouting({
  locales: ["ar", "en", "fa"],
  defaultLocale: "ar",
  localePrefix: "always", // every URL is prefixed: /ar/about, /en/about, /fa/about
});
```

### `src/i18n/request.ts`

Loads messages dynamically per locale — branches explicitly on `ar`/`fa` with `en` as the
`defaultLocale` fallback:

```typescript
export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = hasLocale(routing.locales, requested) ? requested : routing.defaultLocale;

  let mod: { default: Record<string, unknown> };
  if (locale === "ar") {
    mod = await import("../../messages/ar.json");
  } else if (locale === "fa") {
    mod = await import("../../messages/fa.json");
  } else {
    mod = await import("../../messages/en.json");
  }
  return { locale, messages: mod.default };
});
```

### `next.config.ts`

```typescript
import createNextIntlPlugin from "next-intl/plugin";
const withNextIntl = createNextIntlPlugin("./src/i18n/request.ts");
export default withNextIntl(nextConfig);
```

### `src/proxy.ts`

The next-intl middleware for locale-aware routing lives in `src/proxy.ts` —
`createMiddleware(routing)` with a matcher excluding `api`, `trpc`, `_next`, `_vercel`, and
static files (there is no `middleware.ts` in this repo).

## Supported Locales

| Locale | Language | Direction           |
| ------ | -------- | ------------------- |
| `ar`   | Arabic   | RTL (right-to-left) |
| `en`   | English  | LTR (left-to-right) |
| `fa`   | Farsi    | RTL (right-to-left) |

## RTL Handling

The `DirectionSetter` component (exported from
`src/components/providers/DirectionProvider.tsx`) sets the `dir` attribute on `<html>`.
It renders **null** — it wraps no children:

```typescript
// src/components/providers/DirectionProvider.tsx (~9-14)
function getDir(locale: string): string {
  return locale === "ar" || locale === "fa" ? "rtl" : "ltr";
}

export function DirectionSetter({ locale }: { locale: string }) {
  useEffect(() => {
    document.documentElement.dir = getDir(locale);
  }, [locale]);
  return null;
}
```

### Per-Message Bidi in Chat

Chat messages can be in a different language than the UI locale, so direction is resolved
**per message** rather than per page (commit c9f4f21):

- `localeDirection(locale?)` in `src/lib/locale.ts` maps a message locale to `"rtl"` / `"ltr"`
  (`"auto"` when unknown)
- Assistant markdown renders as `<Markdown dir={localeDirection(message.locale)}>` in
  `src/components/chat/ChatMessageList.tsx`
- User bubbles use `dir="auto"` so mixed-script text is laid out by its own content

This keeps an Arabic answer rendering RTL even while the surrounding UI is in English.

### RTL Component Considerations

- **Switch component**: Uses `dir="ltr"` on the root to prevent thumb overflow in RTL mode
- **Instagram / website URL inputs**: Use `dir="ltr"` to keep URLs displayed LTR even in RTL
- **Icons in InputGroup**: Positions are flipped automatically by Tailwind's `rtl:` modifier
- **Leaflet maps**: Unaffected by document direction

All three locale files are guarded by an ICU-validity test,
`src/i18n/__tests__/messages.test.ts`, which parses every string in `en.json`, `ar.json`, and
`fa.json` with the ICU MessageFormat parser.

## Translation Files

```
messages/
├── ar.json     # Arabic (primary locale)
├── en.json     # English (fallback)
└── fa.json     # Farsi
```

The `en.json` file serves as the source of truth — add new keys here first, then translate to `ar.json` and `fa.json`.

## Adding a New Translation Key

1. Add the key to all three locale files (`en.json`, `ar.json`, `fa.json`)
2. Use the key in components via `useTranslations()`:

```typescript
import { useTranslations } from "next-intl";

function MyComponent() {
  const t = useTranslations("profile");
  return <h1>{t("fullName")}</h1>;
}
```

Namespaces are optional — `useTranslations("auth")` scopes to the `auth` object, while `useTranslations()` returns the full message tree.

## Error Code Translation Pattern (`translation_key`)

Every user-facing API error carries a `translation_key` from the backend, mapped to a localized message under the `errors` namespace in all three locale files:

```json
{
  "errors": {
    "user_not_found": "User not found",
    "chat_limit_reached": "Chat limit reached"
  }
}
```

Frontend helpers in `src/lib/api.ts`:

- `extractApiError(error, fallback)` — extracts `error.message` from the envelope (with legacy `detail` fallback)
- `extractTranslationKey(error)` — extracts `translation_key` for i18n lookup

Pattern in components:

```tsx
const errorsT = useTranslations("errors");
const key = extractTranslationKey(error);
toast.error(key ? errorsT(key) : extractApiError(error, t("error")));
```

Chat errors (`lib/chat.ts` `CHAT_ERROR_CODES`) also map to `errors.*` keys: `chat_failed`, `chat_limit_reached`, `conversation_closed`, `conversation_not_found`, `chat_not_available`, `embedding_failed`.

### Adding a New Translation Key

1. Backend adds `translation_key=E.NEW_KEY` to the raise (see `api/docs/error-codes.md`).
2. Add `"new_key": "English text"` to `messages/en.json` under `errors`.
3. Add `"new_key": "النص العربي"` to `messages/ar.json` under `errors`.
4. Add `"new_key": "متن فارسی"` to `messages/fa.json` under `errors`.
